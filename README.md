# Cats vs Dogs — MLOps Pipeline (M1: Model Development & Experiment Tracking)

Binary image classification (Cats vs Dogs) for a pet-adoption platform.
This milestone covers: **data & code versioning (Git + DVC), a baseline CNN,
and MLflow experiment tracking.**

> Dataset used here: the standard Kaggle "Cats and Dogs" dataset, laid out as
> `data/raw/PetImages/Cat/*.jpg` and `data/raw/PetImages/Dog/*.jpg`. A small
> sample (9 images/class) is included so you can smoke-test the pipeline
> immediately; drop in the full ~25,000-image dataset the same way before
> your real training run.

## 1. Project structure

```
mlops-pet-classifier/
├── data/
│   ├── raw/PetImages/{Cat,Dog}/        # raw images (DVC-tracked, not git)
│   └── processed/{train,val,test}/{Cat,Dog}/   # generated by preprocessing (DVC-tracked)
├── src/
│   ├── utils.py                # config loading, seeding, device selection
│   ├── data_preprocessing.py   # validate, resize, split raw -> processed
│   ├── dataset.py              # PyTorch Dataset/DataLoader + augmentation
│   ├── model.py                # SimpleCNN + predict() inference utility
│   └── train.py                # training loop + MLflow logging
├── tests/
│   ├── test_preprocessing.py   # unit tests for preprocessing functions
│   └── test_model.py           # unit tests for model + inference function
├── notebooks/
│   └── 01_eda.ipynb            # quick exploratory look at the dataset
├── models/                     # trained model artifacts land here (model.pt)
├── mlflow.db / mlruns/         # local MLflow tracking store (generated)
├── params.yaml                 # single source of truth for hyperparameters
├── dvc.yaml                    # DVC pipeline: preprocess -> train
├── requirements.txt
├── .gitignore
└── .dvcignore
```

## 3. Data & code versioning (Git + DVC)

```bash
# Initialize git (skip if you already have a repo)
git init
git add .
git commit -m "Initial project scaffold for M1"

# Initialize DVC
dvc init
git add .dvc .dvcignore
git commit -m "Initialize DVC"

# Track the raw dataset with DVC (not Git - it's binary/large)
dvc add data/raw/PetImages
git add data/raw/PetImages.dvc data/raw/.gitignore
git commit -m "Track raw dataset with DVC"

# (Optional but recommended) configure a local DVC remote to push to,
# simulating cloud storage without needing external credentials:
dvc remote add -d localremote ../dvc-storage
dvc push
```

After you run preprocessing (step 4) you can version the processed data too:

```bash
dvc add data/processed
git add data/processed.dvc
git commit -m "Track processed dataset with DVC"
dvc push
```

> Swap in Git-LFS instead of DVC if you prefer — just `git lfs track "*.jpg"`
> and commit normally; the rest of the pipeline is unaffected.

## 4. Run the pipeline

You can either run the two stages manually, or let DVC orchestrate them via `dvc.yaml`.

**Manual:**
```bash
python src/data_preprocessing.py     # data/raw -> data/processed (train/val/test)
python src/train.py                  # trains SimpleCNN, logs to MLflow, saves models/model.pt
```

**Via DVC pipeline (reproducible, re-runs only stages whose deps/params changed):**
```bash
dvc repro
```

## 5. View experiment tracking

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
# then open http://localhost:5000
```

> We use a SQLite tracking store (`mlflow.db`) rather than the plain
> `./mlruns` folder store, since recent MLflow versions have put the
> folder-based store into maintenance mode. Artifacts (plots, models)
> still land on disk under `mlruns/`.

Each run logs:
- **Params:** epochs, batch size, learning rate, image size, split ratios, seed
- **Metrics (per epoch):** train/val loss & accuracy, plus final test accuracy
- **Artifacts:** `loss_curves.png`, `confusion_matrix.png`, `classification_report.txt`,
  and the trained model itself (both as an MLflow model and as `model.pt`)

## 7. Notes on the baseline model

`src/model.py` defines `SimpleCNN` — a compact 3-conv-block CNN (kept small
so it trains quickly on CPU for iteration). Swap in a deeper architecture or
transfer learning (e.g. ResNet18) later by editing `model.py`; `train.py`
and the M2 FastAPI service don't need to change since both only depend on
the `SimpleCNN` interface (`forward()`, and `predict()` from `model.py`).

## 8. Troubleshooting

**`ERROR: cannot import name '_DIR_MARK' from 'pathspec.patterns.gitwildmatch'` on `dvc init`**
A `pathspec`/`dvc` version mismatch. Run `pip install "pathspec<0.12,>=0.10.3"` and retry,
or `pip install --upgrade dvc`.

**`'.dvc' exists. Use -f to force.`**
A previous `dvc init` partially ran. Either `dvc init -f`, or delete the `.dvc` folder first.

**`ModuleNotFoundError: No module named 'pkg_resources'`**
MLflow still uses `pkg_resources` internally, which needs `setuptools` — not installed
by default on Python 3.12+. Run `pip install setuptools` (already pinned in
`requirements.txt`, but worth knowing if you hit it elsewhere).

**`MlflowException: The filesystem tracking backend ... is in maintenance mode`**
Newer MLflow versions deprecate the plain `./mlruns` folder store. This project already
uses `sqlite:///mlflow.db` (see `params.yaml`) to avoid it — make sure you're on the
latest `train.py`/`params.yaml` from this repo.

**`MlflowException: Could not find a registered artifact repository for: C:\...\mlruns\...`**
Happens if `mlflow.create_experiment(...)` gets a raw OS path instead of a `file://` URI —
common on Windows. Already fixed here via `artifact_dir.as_uri()` in `train.py`. If you
still hit it, delete the stale `mlflow.db`/`mlruns` (it caches the broken path) and rerun.

**`MlflowException: If serialization_format is set to 'pt2', torch package version must be >= 2.4`**
Newer MLflow defaults `mlflow.pytorch.log_model()` to the "pt2" export format, which
needs torch ≥ 2.4. This project pins torch 2.2.2, so `train.py` explicitly passes
`serialization_format="pickle"` to avoid it. The call is also wrapped in `try/except`
so a logging-format issue never loses your trained model — `model.pt` is always saved
as a plain artifact regardless.

**Repeated `[transformers] Disabling PyTorch because PyTorch >= 2.4 is required...` spam**
Harmless — some dependency (likely mlflow, probing for optional integrations) triggers
a lazy `transformers` import. It reprints on every DataLoader worker restart. Two things
mitigate it: `train.py` sets `TRANSFORMERS_VERBOSITY=error` at startup, and `dataset.py`
uses `persistent_workers=True` so workers aren't torn down and respawned every epoch
(this also meaningfully speeds up training — see next point).

**Training is very slow on CPU (took over an hour on the full dataset)**
A few contributing factors and what to do about them:
1. **No GPU in use.** Check with `python -c "import torch; print(torch.cuda.is_available())"`
   and `nvidia-smi`. If you have an NVIDIA GPU but this prints `False`, you have the
   CPU-only torch wheel — reinstall with a CUDA-matched index, e.g.:
   ```bash
   pip uninstall torch torchvision -y
   pip install torch==2.2.2 torchvision==0.17.2 --index-url https://download.pytorch.org/whl/cu121
   ```
   (swap `cu121` for the CUDA version `nvidia-smi` reports). If you have no NVIDIA GPU,
   CPU is expected and this is a normal (if slow) baseline run.
2. **DataLoader workers were respawning every epoch** on Windows (spawn-based
   multiprocessing re-imports the whole stack each time) — fixed via
   `persistent_workers=True` in `dataset.py`.
3. **CPU training ~20k 224×224 images with augmentation is inherently slow.** For faster
   iteration while developing, temporarily lower `epochs` or `image_size` in `params.yaml`,
   or pass `--epochs 2` on the command line; do your final graded run at full settings.

## 9. M2 — Model Packaging & Containerization

`src/app.py` wraps `models/model.pt` in a FastAPI REST service.

**Endpoints:**
| Method | Path | Body | Purpose |
|---|---|---|---|
| GET | `/health` | — | Liveness/readiness; reports `model_loaded` and `device` |
| POST | `/predict` | `multipart/form-data`, field `file` | Predict from an uploaded image file |
| POST | `/predict/base64` | JSON `{"image_base64": "..."}` | Predict from a base64-encoded image string |

Response shape (both predict endpoints):
```json
{"label": "Dog", "class_index": 1, "probabilities": {"Cat": 0.12, "Dog": 0.88}}
```

### 9.1 Run locally (no Docker)

```bash
pip install -r requirements.txt      # picks up fastapi/uvicorn/python-multipart added for M2
uvicorn app:app --app-dir src --reload --host 0.0.0.0 --port 8000
```

Open **http://localhost:8000/docs** for interactive Swagger UI — you can upload a file and hit
`/predict` right from the browser, no curl/Postman needed.

**curl (file upload):**
```bash
curl -X POST http://localhost:8000/predict -F "file=@path/to/pet.jpg"
```

**curl (base64) — PowerShell:**
```powershell
$b64 = [Convert]::ToBase64String([IO.File]::ReadAllBytes("pet.jpg"))
curl -X POST http://localhost:8000/predict/base64 `
     -H "Content-Type: application/json" `
     -d (@{image_base64=$b64} | ConvertTo-Json)
```

**Or use the included smoke-test script (checks all 3 endpoints in one go):**
```bash
python scripts/smoke_test.py --image path/to/pet.jpg
```

**Postman:** for `/predict`, set method POST, body → form-data, key `file` (type: File), pick an
image. For `/predict/base64`, body → raw → JSON, `{"image_base64": "<paste base64 string>"}`.

### 9.2 Build and run with Docker

Requires `models/model.pt` to already exist locally (train first — the image build doesn't train).

```bash
docker build -t pet-classifier-api:latest .
docker run -p 8000:8000 pet-classifier-api:latest
```

Then hit the same endpoints as above — nothing changes except it's now containerized:
```bash
curl http://localhost:8000/health
python scripts/smoke_test.py --image path/to/pet.jpg
```

### 9.3 Troubleshooting

**`/predict` returns `503 Model not loaded`**
Either you haven't run `python src/train.py` yet, or (for Docker) `models/model.pt` didn't
exist at build time so `COPY models/model.pt` in the Dockerfile would have failed the build
outright — rebuild after training.

**`422 Unprocessable Entity` on `/predict`**
Usually means the form field isn't named `file`, or you're sending JSON to `/predict` instead
of `/predict/base64` (or vice versa). Check `/docs` for the exact expected shape.

**File upload fails with a multipart-related error**
`python-multipart` must be installed (`pip install -r requirements.txt` covers it) — FastAPI
needs it specifically to parse `UploadFile`/form-data.
